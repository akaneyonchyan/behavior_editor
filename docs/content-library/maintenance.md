# 维护方式

更新日期：2026-10-17。

## 正常修改流程

1. 在飞书修改前，确认当前原文、工程表和现有条目的含义；参见[规则来源](sources.md)。检查是否已有同义条目，记录本次依据和影响。
2. 留存修改前的行或飞书历史版本。备份在团队内部保存，不提交内部原表到公开仓库。
3. 新增对象后再关联属性/Buff。填写稳定标识、名称、说明、启用；属性填写数据类型，属性/Buff选择适用对象。未核实条目按待核对处理，必要时停用。
4. 等待约每5分钟触发的 GitHub Actions。工作流读取三表、校验、生成快照并构建发布。排队或失败时会更久，延迟没有保证上限。
5. 页面点击“刷新数据”或等待60秒检查；核对飞书同步时间。手动刷新不会触发新的飞书读取或 GitHub 工作流。
6. 在一个测试行为中选择对象，检查候选范围、名称、说明和旧引用；验证新快照实际包含预期修改后，再通知团队。

交接记录至少包含日期、修改人、对象/属性/Buff的 ID、旧值→新值、来源章节、影响范围、发布结果和待确认项。不要只写“已同步”。

## 同步与公开边界

飞书三表 → server/feishu.mjs 读取转换 → shared/library-model.mjs 校验 → scripts/export-public-library.mjs 生成 public/data/library.json → Pages 发布 → 网页获取与缓存。

三表内容中的名称、说明、标识及适用关系会成为公开快照，包括停用条目。不要在条目说明中填写密钥、个人敏感数据或不能公开的内容。飞书记录授权不会被发布成浏览器凭证。

网页刷新失败会保留当前数据；比本机缓存更早的 syncedAt 会被拒绝。数据语义回退也应重新发布新时间的快照，而不是上传旧时间快照。

## 管理员配置

Pages 的 Source 选择 GitHub Actions。Repository Secrets 需要以下六项：

| 名称 | 用途 |
|---|---|
| FEISHU_APP_ID | 飞书自建应用 ID |
| FEISHU_APP_SECRET | 应用密钥 |
| FEISHU_BASE_TOKEN | 多维表格 app token |
| FEISHU_OBJECT_TABLE | 对象表 ID |
| FEISHU_ATTRIBUTE_TABLE | 属性表 ID |
| FEISHU_BUFF_TABLE | Buff 表 ID |

应用需已发布、具备读取多维表格记录的权限，并获该表格的访问授权；组织管理员审批按团队规则处理。生产只读同步不要求网页用户填写密钥。不要放到 VITE_ 变量、源码、行为 JSON 或浏览器存储。

缺少部分 Secrets 时发布失败；只有 push 事件且全部未配置时才允许首次仅发布编辑器。当前工作流没有 workflow_dispatch 手动入口；正常由推送和计划任务触发。检查 Actions 最新运行及失败步骤；修复原因后可按 GitHub 的重跑入口重跑已有任务。

## 排查表

| 现象 | 检查顺序 |
|---|---|
| 飞书改了网页不变 | Actions 是否成功、是否排队、页面同步时间、网页刷新结果 |
| 应用授权失败 | App ID/Secret、应用发布状态；不要把密钥贴到日志或聊天 |
| 飞书接口错误 | 表格 token/表 ID、应用权限、表格协作者授权、错误码 |
| 重复标识或名称 | 同表全部行，包括停用行；不要删除被引用 ID 来凑通过 |
| 适用对象无效 | 是否关联了对象表真实记录，是否删除了被引用对象，字段是否误改成文本 |
| 条目存在但下拉没有 | 启用状态、对象类型、适用对象、属性/Buff分栏、页面是否仍为旧快照 |
| 本地快照较新 | 使用新发布时间重新发布纠正数据，不强行清空所有用户缓存 |

读取或校验失败不会继续部署该次构建，线上保留此前站点。修复源数据后再次同步即可。

## 迭代与回退

新增表或字段不能只改飞书：需同步设计 JSON 结构、转换器、校验器、筛选与 UI、旧快照兼容及测试。数据语义改变先评估所有现有行为引用，提供迁移方案，再更新使用说明。

回退数据优先恢复原行的字段与关联，保留稳定 ID，再重新发布；重新创建一行会改变 record_id，尤其要检查关联字段。旧后台的写入/合并接口不是当前线上维护路径，不应直接调用来绕过飞书维护流程。
